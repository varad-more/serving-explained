## The same prompt, computed again

Many requests start the same way.
Different requests often share common parts, such as a <GlossaryTerm id="system-prompt">system prompt</GlossaryTerm> that an application puts first in every request (<SourceLink id="zheng2024" at="§3" />).
Call a request's opening tokens its <GlossaryTerm id="prefix">prefix</GlossaryTerm>.
Two requests that share a prefix compute the same keys and values for it (<SourceLink id="vllm-apc-doc" />).

Figure 4.1's workload has <Num value={F.requests} kind="simulated" badge={false} /> requests, arriving at about <Num value={F.rate} digits={1} unit="per second" kind="simulated" />.
<Num value={F.fraction} unit="%" kind="simulated" badge={false} /> of them start with one <Num value={F.prefixLen} kind="simulated" />-token system prompt.
The KV pool holds <Num value={F.capacity} kind="simulated" badge={false} /> tokens in <Num value={F.blocks} kind="simulated" /> blocks, and at most <Num value={F.maxNumSeqs} kind="simulated" /> requests run at once.

<Claim id="repeated-prefill">With caching off, <Num value={F.repeated.sharers} kind="simulated" /> requests compute the <Num value={F.prefixLen} kind="simulated" badge={false} />-token prefix. The <Num value={F.repeated.preempted} kind="simulated" badge={false} /> of them that get preempted compute it again, so the prefix costs <Num value={F.repeated.tokens} kind="simulated" /> tokens of prefill. Figure 4.1 labels r{F.repeated.example}'s second prefill as a recompute.</Claim>
<Link to="/paged-attention/">Chapter 2</Link> covered <GlossaryTerm id="preemption">preemption</GlossaryTerm>: a preempted request gives up its blocks, and with caching off it computes its tokens again.

</ChapterStep>

## Each full block gets a key

vLLM's <GlossaryTerm id="prefix-caching">prefix caching</GlossaryTerm> gives each full block a <GlossaryTerm id="block-key">key</GlossaryTerm> (<SourceLink id="vllm-apc-doc" at="L13–19" />).
The key is a hash of the block's <GlossaryTerm id="parent-key">parent key</GlossaryTerm>, its tokens, and extra keys that keep different adapters, images, or tenants apart.
Because each key includes its parent's, a key stands for the whole prefix up to its block.

<Claim id="one-token-changes-chain">So changing a token in a full block keeps every earlier key and changes the key of its own block and every block after. We checked our engine's keys for every token of a 64-token prompt at block sizes 4, 8, and 16.</Claim>
Figure 4.2 shows Figure 4.1's system prompt: <Num value={F.chain.full} kind="simulated" badge={false} /> full blocks of <Num value={F.blockSize} kind="simulated" badge={false} /> tokens, and <Num value={F.chain.partial} kind="simulated" /> tokens left over.

<Claim id="full-blocks-only">Only full blocks get keys (<SourceLink id="vllm-apc-doc" at="L22" />). In both of this chapter's workloads, every block the engine caches is full.</Claim>

vLLM hashes with sha256 by default (<SourceLink id="vllm-apc-doc" at="Note 2" />).
Our engine uses a 53-bit hash and checks the tokens on every hit, so a collision cannot give a wrong hit (<a href={`${SIM}#3-data-structures`}>SIM.md §3</a>).

</ChapterStep>

## A hit reuses the chain

At <GlossaryTerm id="admission">admission</GlossaryTerm>, the engine hashes a request's full blocks and looks them up in order (<SourceLink id="vllm-apc-doc" at="L143" />).
It stops at the first miss: a missing block means every later one misses too (<SourceLink id="vllm-src" at="v1/core/single_type_kv_cache_manager.py L797–805" />).
Each block found is a <GlossaryTerm id="cache-hit">cache hit</GlossaryTerm>.
The request's <GlossaryTerm id="block-table">block table</GlossaryTerm> points at that block, and its <GlossaryTerm id="reference-count">reference count</GlossaryTerm> goes up by one (<SourceLink id="vllm-apc-doc" at="L146–147" />).

<Claim id="hit-walks-chain">In Figure 4.3, each sharing request after the first hits <Num value={F.hit.perSharer} kind="simulated" /> tokens whenever those full blocks are still cached when it is admitted.</Claim>
<Claim id="refcount-counts-sharers">A prefix block's reference count is the number of running requests whose tables hold it: up to <Num value={F.hit.mostSharers} kind="simulated" /> at once here.</Claim>

<Claim id="caching-lowers-ttft-and-prefill">Caching cuts mean <GlossaryTerm id="ttft">time to first token (TTFT)</GlossaryTerm> from <Num value={F.hit.ttftOff} digits={2} unit="s" kind="simulated" badge={false} /> to <Num value={F.hit.ttftOn} digits={2} unit="s" kind="simulated" />. Prefill work falls from <Num value={F.hit.prefillOff} kind="simulated" badge={false} /> tokens to <Num value={F.hit.prefillOn} kind="simulated" />.</Claim>

</ChapterStep>

## Eviction

A cached block with no references stays keyed in the <GlossaryTerm id="free-queue">free queue</GlossaryTerm> (<SourceLink id="vllm-apc-doc" at="L202–206" />).
New allocations take blocks from the head of that queue.
Taking a cached block is an <GlossaryTerm id="eviction">eviction</GlossaryTerm>: its key leaves the cache.

vLLM puts a freed block without a key at the front of the queue, and one with a key at the back (<SourceLink id="vllm-src" at="v1/core/block_pool.py L777–808" />).
So free blocks without a key go first; among cached blocks, the <GlossaryTerm id="lru">least recently used</GlossaryTerm> is nearest the head.
<Claim id="lru-evicts-head">In Figure 4.5, every eviction takes the block at the head of the queue, eviction order 1 in the grid.</Claim>
<Claim id="evict-only-when-needed">And a cached block is evicted only when no free block without a key is left.</Claim>

Figure 4.5's workload has <Num value={F.pressure.prefixes} kind="simulated" badge={false} /> system prompts of <Num value={F.pressure.prefixLen} kind="simulated" /> tokens each.
Together they need <Num value={F.pressure.needed} kind="simulated" badge={false} /> blocks, and the pool has <Num value={F.pressure.blocks} kind="simulated" />.
<Claim id="evictions-happen">The engine evicts <Num value={F.pressure.evictions} kind="simulated" /> times.</Claim>
<Claim id="pressure-lowers-hit-rate">The hit rate falls to <Num value={F.pressure.rate} digits={1} unit="%" kind="simulated" badge={false} />, against <Num value={F.pressure.sharedRate} digits={1} unit="%" kind="simulated" /> on Figure 4.3's workload, which shares one longer system prompt in a bigger pool.</Claim>
<Claim id="more-blocks-more-hits">More capacity keeps more prefixes. From <Num value={F.pressure.capacities[0]?.capacity ?? 0} kind="simulated" badge={false} /> to <Num value={F.pressure.capacities.at(-1)?.capacity ?? 0} kind="simulated" badge={false} /> tokens of KV, the hit rate never falls, and it rises from <Num value={F.pressure.capacities[0]?.rate ?? 0} digits={1} unit="%" kind="simulated" badge={false} /> to <Num value={F.pressure.capacities.at(-1)?.rate ?? 0} digits={1} unit="%" kind="simulated" />.</Claim>

</ChapterStep>

## Not every request gets faster

Figure 4.6 runs caching off and on side by side, in lockstep.
Set its share of requests with a prefix to 0%, and the two runs look alike.

<Callout kind="misconception">

"Prefix caching makes every request faster."
It saves prefill only when prefixes repeat and their blocks are still cached.
<Claim id="unique-no-hits">With no shared prefix, Figure 4.3's workload gets no hits: <Num value={F.myth.uniqueRate} digits={0} unit="%" kind="simulated" />. Neither run preempts, and every request's TTFT is exactly the same with caching on and off.</Claim>
<Claim id="self-hit-after-preemption">One exception: a preempted request can hit its own blocks, which keep their keys when freed. In a small run of <Num value={F.myth.selfRequests} kind="simulated" badge={false} /> unrelated prompts, r{F.myth.selfReq} is preempted, and when admitted again it hits <Num value={F.myth.selfCached} kind="simulated" /> of its own tokens.</Claim>
That follows vLLM, which frees a preempted request's blocks without dropping their keys (<SourceLink id="vllm-src" at="v1/core/sched/scheduler.py L1540–1583, v1/core/block_pool.py L777–808" />).

Our reasoning: a decode step reads the whole context, whether it came from a hit or not.
vLLM does so too by default; its cascade attention, which can share those reads, is off unless enabled (<SourceLink id="vllm-src" at="config/model.py L284–290" />).
<Claim id="decode-cost-unchanged">In our engine, a request whose first <Num value={F.myth.pairHit} kind="simulated" /> tokens hit decodes in steps exactly as long as when they were computed.</Claim>
<Claim id="caching-raises-p50-itl">Decode can even get slightly slower. With caching on, each decode step runs more requests, <Num value={F.myth.batchOn} digits={1} kind="simulated" badge={false} /> against <Num value={F.myth.batchOff} digits={1} kind="simulated" /> on average. So p50 <GlossaryTerm id="itl">inter-token latency (ITL)</GlossaryTerm> rises, from <Num value={1000 * F.myth.p50Off} digits={1} unit="ms" kind="simulated" badge={false} /> to <Num value={1000 * F.myth.p50On} digits={1} unit="ms" kind="simulated" />. p99 ITL falls, from <Num value={1000 * F.myth.p99Off} unit="ms" kind="simulated" badge={false} /> to <Num value={1000 * F.myth.p99On} unit="ms" kind="simulated" />.</Claim>
<GlossaryTerm id="percentile">p50 and p99</GlossaryTerm> are the median and the slowest 1%.
Our reasoning: with caching off, longer prefills and more preemptions stall decodes, which is what p99 sees.

</Callout>

## Another design: RadixAttention

SGLang's RadixAttention keeps cached KV in a <GlossaryTerm id="radix-tree">radix tree</GlossaryTerm>, in pages of one token, so it matches token by token (<SourceLink id="zheng2024" at="§3" />).
It evicts the least recently used leaf first, never a node in use, and cached and running requests share one memory pool.
Its scheduler runs requests with longer cached prefixes first; ours serves requests in arrival order.
Our comparison, not the paper's: one-token pages lose nothing to partial blocks, while vLLM recomputes each prefix's partial last block (<SourceLink id="vllm-apc-doc" at="L22" />).

</ChapterStep>

## More than one replica

A large service runs several <GlossaryTerm id="replica">replicas</GlossaryTerm> of a model.
Our reasoning: with several replicas, a hit needs the request to land on the replica that holds its prefix.
The author's kv-transfer-tax benchmark has a replica balancer, and it routes by load or in turn, never by prefix (<a href={`${KVTT}/proxy/replica_lb.py#L56-L75`}>proxy/replica_lb.py L56–75</a>, <SourceLink id="bench-kvtt" />).
It runs separate servers (<a href={`${KVTT}/README.md#L113-L115`}>README L113–115</a>), so each keeps its own cache; that last part is our inference.

</ChapterStep>

## What this leaves out

- Extra keys for adapters, images, and tenants, and sha256: our keys hash only the parent key and the tokens (<SourceLink id="vllm-apc-doc" at="L13–19" />, <a href={SIM9}>SIM.md §9.8</a>).
- Real text: our tokens are synthetic numbers, with no tokenizer or chat template. Real prefixes hit only when their token ids match (<a href={SIM9}>SIM.md §9.5</a>).
- Cache-aware scheduling: we serve requests in arrival order only (<SourceLink id="zheng2024" at="§3" />, <a href={SIM9}>SIM.md §9.10</a>).
- Cascade attention, which can share decode reads of a common prefix; vLLM leaves it off by default (<SourceLink id="vllm-src" at="config/model.py L284–290" />).
- vLLM's asynchronous scheduling, which shifts TTFT; ours plans each step after the last ends (<a href={SIM9}>SIM.md §9.3</a>).
- More than one replica (<a href={SIM9}>SIM.md §9.1</a>).
- Moving KV to CPU memory or disk (<a href={SIM9}>SIM.md §9.13</a>).
- A real pool: ours holds <Num value={F.capacity} kind="simulated" badge={false} /> tokens and at most <Num value={F.maxNumSeqs} kind="simulated" /> requests at once (<a href={SIM9}>SIM.md §9.14</a>). vLLM's default <GlossaryTerm id="max-num-seqs">max_num_seqs</GlossaryTerm> is 256 on GPUs under 70 GB (<SourceLink id="vllm-src" at="engine/arg_utils.py L2866–2895" />).
- Measured step times: ours come from a roofline with no step overhead (<a href={SIM9}>SIM.md §9.2</a>).
- The CPU time the prefix cache's own bookkeeping takes (<a href={SIM9}>SIM.md §9.2</a>).
- Swapping preempted requests to CPU memory: we recompute, as vLLM V1 does (<a href={SIM9}>SIM.md §9.9</a>).
- vLLM's reserved null block: all our blocks are usable (<a href={SIM9}>SIM.md §9.12</a>).
